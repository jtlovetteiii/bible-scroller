# Email agent — host setup

The agent watches a Gmail inbox for an emailed order of service, builds a
ProPresenter-style deck with the `gen_service` skill, publishes it to S3, and
replies to the minister with a link. It runs unattended on one always-on box.

- **What it is and how it works:** [`specs/email-agent.md`](../specs/email-agent.md)
- **How decks get to the minister:** [`specs/deck-publishing.md`](../specs/deck-publishing.md)

This file is only about **getting it running on a host**. It does not repeat the
design; read the specs for that.

---

## The three-step install

On a **Debian/Ubuntu x86_64** box that stays on:

```bash
# 1. Clone it somewhere permanent (not /tmp, not a home you might wipe)
git clone <repo-url> /srv/bible-scroller
cd /srv/bible-scroller

# 2. Create the AWS profile by hand — this is the ONE thing the script won't do
aws configure --profile cbc-wilm-agent      # access key + secret for the IAM user

# 3. Run the installer
sudo ./scripts/install-agent-host.sh
```

Step 3 finishes by running the healthcheck **through systemd, as the service
user** and fails loudly if it is not `HEALTHY`. If it prints HEALTHY, the agent
is live and polling every minute.

**Re-run the script whenever anything changes** — after a `git pull`, a new
token, an edited `.env`. It is idempotent: every step is check-then-act, so on an
unchanged host it does nothing and exits 0. It never duplicates the timer,
appends a second env line, or overwrites a credential that is already correct.

```bash
sudo ./scripts/install-agent-host.sh --check   # report drift, change nothing
```

`--check` exits 0 when the host is converged, 1 when something would change.

### What the installer does

| Step | Idempotency |
|---|---|
| Node ≥ 18 (NodeSource) | Skipped entirely if `node -v` already ≥ 18. The apt list file is content-compared, never appended. |
| `uv` → `/usr/local/bin` | Skipped if `uv` is already on PATH. Never silently upgrades a working toolchain. |
| Python ≥ 3.11 | Uses the system python3 when it qualifies; otherwise `uv python install` fetches a managed one. |
| `uv sync --frozen` | Reconciles `.venv` to `uv.lock`; already a no-op when in sync. Runs **as the service user** so `.venv` isn't root-owned. |
| Render `examples/2026-06-28.deck.json` | Read-only probe to a temp file. |
| Credential checks | Assert-only. The script **never writes a secret** and never overwrites one. |
| `*.service` / `*.timer` | Rendered to a temp file and `cmp`'d; only written if different, and `daemon-reload` only runs if a unit actually changed. |
| `enable` / `start` the timer | Gated on `is-enabled` / `is-active`. One unit by name — there is no way to get two. |
| Healthcheck | Read-only apart from the S3 probe object (see below). |

## Prerequisites the script installs for you

Documented here because they are easy to miss when reading the Python:

- **Node ≥ 18 — a hard *runtime* dependency, not a build one.** `publish.py`
  shells out to `node scripts/build-deck.js`. A Python-only box installs
  cleanly, passes every Python check, and then fails **at publish time — after
  the deck is built**, which is the worst possible moment. The installer
  installs it, verifies it, and renders a real deck once to prove it.
- **uv** — manages the Python environment.
- **Python ≥ 3.11** — `pyproject.toml`'s `requires-python`. Ubuntu 22.04 ships
  3.10, which is *not* enough; the installer lets `uv` fetch its own interpreter
  rather than bolting on a PPA.

The **AWS CLI is not needed by the agent** (boto3 covers publishing). It is only
convenient for step 2, and for the operator-run `npm run sync-templates`, which
can be done from a laptop.

## Credentials

The installer verifies all of these and refuses to install if any is missing. It
does not create them — a secret typed into a prompt can't be re-run unattended,
and a secret generated by the script would clobber a working one on the next run.

### 1. `CLAUDE_CODE_OAUTH_TOKEN` → `.env` at the repo root

The agent bills the **subscription**, not pay-per-token. Generate the token on a
machine with a browser (it lasts ~1 year):

```bash
claude setup-token
```

Put it in `/srv/bible-scroller/.env` (gitignored; the installer chmods it 0600):

```
CLAUDE_CODE_OAUTH_TOKEN=<token>
```

> **`ANTHROPIC_API_KEY` must be UNSET.** If present it *silently* outranks the
> OAuth token and bills a pay-per-token API account instead of the subscription.
> Nothing about the output looks different. There are three guards: the unit
> scrubs it with `UnsetEnvironment=`, `config.assert_subscription_auth()` hard
> fails, and the installer **refuses to install if `.env` declares it** — because
> `config.py` calls `load_dotenv()`, a key in `.env` would be re-injected *after*
> systemd scrubbed it, and `UnsetEnvironment=` cannot prevent that.

### 2. AWS — the profile you create in step 2

The IAM user `cbc-wilm-agent` can Put/Get/List the deck bucket and deliberately
**cannot Delete**. `healthcheck` asserts `sts:GetCallerIdentity` ends in
`:user/cbc-wilm-agent` and **fails on anything else** — publishing as root would
*work*, which is exactly why it must be rejected rather than tolerated.

> **The systemd foot-gun this design exists to defuse:** systemd does **not**
> give a unit the invoking shell's `HOME`, and boto3 resolves
> `~/.aws/credentials` through it. A profile that works perfectly when you test
> it by hand then silently fails as a service. The unit therefore sets `HOME`,
> `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE` and `AWS_PROFILE` explicitly
> — and the installer proves it by running the healthcheck **through systemd**,
> not from your shell.

Keep the agent key as the **only** AWS identity on this box. If you copy a laptop
`~/.aws/credentials` over, a `[default]` profile can shadow the agent and
reintroduce the ambiguity the assertion exists to catch.

### 3. Gmail — consent is a human act, once, in a browser

`gmail_credentials.json` (the OAuth client) must be at the repo root, then:

```bash
cd /srv/bible-scroller/agent
uv run python -m email_agent.authorize      # opens a browser; writes token.json
```

Run this **as the service user**, on a machine with a browser (or forward the
port / use an SSH tunnel — the token file is what matters, and it can be copied
to the host). **The service must never attempt this**: it cannot answer an OAuth
prompt, and would simply fail every minute.

The OAuth app must be **"In production"** in Google Cloud Console. While it is
"Testing", Google expires the refresh token every 7 days and the agent dies
silently.

## Operating it

```bash
# Watch the agent work
journalctl -u cbc-email-agent.service -f

# Recent failures only
journalctl -u cbc-email-agent.service -p err --since today

# Is the timer scheduled? When does it next fire?
systemctl list-timers cbc-email-agent.timer

# Re-verify credentials in the SERVICE's environment (do this after any change)
sudo systemctl start --wait cbc-email-agent-healthcheck.service
journalctl -u cbc-email-agent-healthcheck.service -n 30 --no-pager

# Force one poll->dispatch pass right now
sudo systemctl start cbc-email-agent.service

# Pause / resume the agent (leaves everything installed)
sudo systemctl stop  cbc-email-agent.timer
sudo systemctl start cbc-email-agent.timer
```

Run the gate without dispatching anything — no claims, no agent, no email sent:

```bash
cd /srv/bible-scroller/agent && uv run python -m email_agent.heartbeat --dry-run
```

### Why a timer and not cron

journald gives you logs you can actually read after a Saturday-night failure;
cron's default failure mode is mailing output into the void. `Persistent=true`
survives reboots. And the unit file is the natural home for the env that both
foot-guns above live in.

`heartbeat.py` is cron-shaped by design — one poll→dispatch pass, then exit — so
it needs no supervisor loop. `dispatcher.py` holds a transactional SQLite claim,
so overlapping runs cannot double-process a thread. Timer overlap is safe.

### Notes

- The healthcheck's AWS probe leaves one object at
  `s3://cbc-wilm-agent-public/_policy-probe/healthcheck.txt`, overwritten on
  every run. It **cannot clean itself up** — the agent has no `DeleteObject` by
  design — and the bucket is public-read, so keep the probe body boring.
- Editing a unit by hand will be reverted on the next install run. Change the
  script instead.
- Everything the units contain is derived from the repo path, so moving the
  checkout means re-running the installer from its new location.
